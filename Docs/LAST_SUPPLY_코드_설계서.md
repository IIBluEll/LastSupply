## 1. 설계 방향과 확인한 환경

**게임 규칙과 진행은 순수 C#으로 처리하고, Unity 연결은 Provider, 화면은 HM CodeBase 기반 MVP, 시간에 따른 표현은 UniTask로 담당한다.**

확장성은 사건·지역·생존자의 데이터를 추가할 수 있는 구조에 우선 배치한다. 새 규칙이 필요한 장비·특성·재굴림까지 현재 구조만으로 처리한다고 약속하지 않는다. 콘텐츠 추가와 규칙 확장을 구분한다.

현재 LastSupply에서 확인한 상태는 다음과 같다.

- Unity 버전 파일: `6000.3.20f1`.
- 게임 전용 C# 코드와 사용자 asmdef는 아직 없다. 기본 TutorialInfo 스크립트와 외부 플러그인이 있는 상태다.
- manifest에는 uGUI `2.0.0`, Input System `1.19.0`, Test Framework `1.6.0`이 등록되어 있다.
- HM CodeBase는 `Packages/manifest.json`에 Git 패키지로 등록되어 있으며, LastSupply의 PackageCache에서 **`1.0.1`**, 캐시 식별자 `fb08effd5ffc`를 확인했다. `Packages/packages-lock.json`의 Git 해시는 `fb08effd5ffc8afab1d4e428c7a1ca9574c3d504`다. 버전은 package.json과 lock 파일, 동작은 실제 Runtime 소스를 기준으로 설명한다.
- UniTask는 UPM manifest 항목이 아니라 `Assets/Plugins/UniTask`에 있으며, 해당 package.json의 버전은 `2.5.11`이다. 같은 라이브러리를 다시 UPM으로 중복 등록하는 것을 전제로 하지 않는다.
- 위 내용은 파일·소스 확인 결과다. Unity의 패키지 처리 완료나 전체 프로젝트 컴파일 성공을 확인한 것은 아니다.

현재 문서 작성에서는 C# 코드, 패키지, Scene, Prefab, Inspector, 프로젝트 설정을 변경하지 않는다.

## 2. 전체 책임과 호출 방향

```text
콘텐츠 에셋(ScriptableObject)
    ├─ 수치·텍스트·ID → 읽기 전용 GameDefinition → GameSession
    └─ 그림·초상화 등 Unity 참조 → UI 구성 시 전달

View → Presenter → LastSupplyGameProvider → GameSession
                                             ├─ ExplorationRules
                                             ├─ SurvivalRules
                                             └─ IRandomSource

GameSession → 확정 결과·상태 사본 → Provider → Presenter → Model / View
                                                    └─ UniTask 연출
```

| 구성 | 소유하는 책임 | 하지 않는 일 |
|---|---|---|
| `GameSession` | 현재 게임 상태, 입력 유효성, 진행 순서, 계산 결과의 단일 적용 | Unity 오브젝트 접근, 연출 대기 |
| `ExplorationRules` | 수색 보상, 사건 후보·범주, 행동 성공, 소음별 귀환 위험 계산 | 상태 직접 변경, 화면 표시 |
| `SurvivalRules` | 치료 가능 여부·회복량, 하루 정산, 승패 계산 | UI 호출, 비동기 작업 |
| `LastSupplyGameProvider` | Unity 진입점, Session 생성·호출, Presenter 구성, 입력 잠금, 작업 수명 | 별도의 게임 상태 복제, 보상 계산식 |
| UI Model / View / Presenter | 확정된 상태의 표시, 입력 전달, 화면별 연출 | 주사위 결과 결정, HP·자원 원본 수정 |
| 콘텐츠 에셋 | 게임 설정과 지역·생존자·사건 정의 | 현재 날짜·HP·전리품 저장 |

게임 상태를 바꾸는 코드는 `GameSession` 안에만 둔다. Provider는 그 작업을 요청하는 유일한 Unity 경로다. Provider와 Session이 각각 다른 진행 상태를 관리하지 않는다. Provider가 가지는 입력 잠금은 연출용이며, 실제 행동 가능 여부는 Session에서 다시 확인한다.

규칙은 값을 받아 계산 결과를 반환한다. 첫 구현에서는 위 두 규칙 클래스로 묶고, 수색·귀환·정산의 복잡도가 실제로 커졌을 때 분리한다. 계산 한 개마다 Manager나 인터페이스를 만들지 않는다.

## 3. 설정 데이터와 실행 상태

### 3.1 콘텐츠 에셋

| 에셋 제안 | 내용 |
|---|---|
| `GameConfig` | 제한 일수, 최대 단계, 초기 자원, 목표 부품, 치료·식량 수치, 기본 수색 보상표, 사건 범주 확률, 소음별 귀환 표, 기본 귀환 사건 정의 |
| `SurvivorConfig` | ID, 이름, 초상화, 최대 HP, 전투·기술 |
| `RegionConfig` | ID, 이름, 설명, 배경, 주 자원, 선택적인 수색 보상표, 사용 일반 사건 목록 |
| `EventConfig` | ID, 범주, 처리 방식, 등장 단계, 상황, 행동과 결과 효과 |
| `GameContentCatalog` | 사용할 GameConfig 및 생존자·지역·일반 사건 에셋 목록 |

Inspector에서는 에셋 참조로 연결하고, 시작 시 ID 기반 데이터로 변환한다. 처음부터 외부 JSON 편집기나 Addressables 로딩 체계를 만들지 않는다.

`GameContentCatalog`에서 `GameDefinition`을 한 번 만든다. 내부의 규칙·지역·생존자·사건 정의는 Unity 타입을 포함하지 않는 값과 문자열로 복사한다. Sprite 등의 참조는 별도로 UI에 전달한다. 이 변환은 게임 규칙이 Unity 에셋이나 편집 중인 값에 직접 의존하지 않게 하기 위한 경계다.

정의 데이터는 외부에 변경 가능한 배열·목록을 그대로 노출하지 않는다. 실행 중 에셋을 수정해도 현재 판의 정의가 바뀌지 않으며, 다시 게임을 만들 때 새 정의를 적용한다. HP나 전리품 변경을 ScriptableObject에 기록하지 않는다.

### 3.2 실행 상태

| 상태 제안 | 내용 |
|---|---|
| `GameRunState` | 날짜, 진행 단계, 은신처 자원, 생존자 상태 목록, 활성 탐색, 미확인 결과, 종료 사유, 상태 Revision |
| `SurvivorState` | 생존자 ID와 현재 HP. 사망 여부는 HP 0으로 판단 |
| `ExpeditionState` | 파견 생존자·지역 ID, 단계 번호, 소음, 임시 전리품, 현재 사건, 직전 단계 사건 ID, 귀환 시작 시 위험 정보 |
| `ResourceAmount` | 식량·의약품·부품 수량을 함께 담는 값. 은신처 보유량·임시 전리품·한 번의 보상은 서로 독립된 값 |

위 상태는 Session 내부 소유다. UI에 전달할 때는 독립된 읽기 전용 `GameSnapshot`을 만든다. UI Model은 그 사본에서 표시 값을 구성하며 게임 상태의 두 번째 원본이 되지 않는다.

사망·전리품 폐기·귀환 정산이 끝나면 활성 탐색을 비운다. 정산 화면에 필요한 이전 값은 별도 정산 결과에 보관한다. 화면을 표시하기 위해 종료된 탐색 상태를 계속 살아 있는 상태로 남기지 않는다.

수색 보상은 자원 종류 하나와 수량 하나로 제한하지 않고 ResourceAmount로 반환한다. 모든 수량이 0이면 미발견이며, 여러 종류가 양수이면 한 번의 복수 보상이다. 현재 기본판의 단일 보상도 같은 구조를 사용한다. 보유량·수색 지급량은 음수가 될 수 없고, 화면의 증감은 적용 전후 값의 차이로 표시한다.

### 3.3 식별자와 열거형

- 생존자·지역·사건은 콘텐츠 ID로 참조한다. `EVENT_001`마다 별도 C# 클래스를 만들거나 ID별 switch문으로 사건 효과를 하드코딩하지 않는다.
- `RESOURCE_TYPE`: `FOOD`, `MEDICINE`, `PARTS`.
- `STAT_TYPE`: `NONE`, `COMBAT`, `TECH`.
- `EVENT_CATEGORY`: `OPPORTUNITY`, `DANGER`. 사건 없음은 범주 추첨 결과로 별도 표현한다.
- `EVENT_MODE`: `INSTANT`, `CHECK`, `CHOICE`.
- `RUN_END_REASON`: `NONE`, `RESCUED`, `ALL_DEAD`, `TIME_EXPIRED`.
- 자원 종류를 새로 추가하면 enum·표시·계산을 함께 검토한다. 현재 세 자원만으로 모든 미래 자원을 지원한다고 가정하지 않는다.

### 3.4 수색 보상표와 보상 묶음

수색 보상표의 값은 단일 수량 대신 보상 항목 목록으로 정의한다. 이 목록은 콘텐츠 정의이며, 현재 판에서 이미 지급한 보상 목록이 아니다.

| 정의 제안 | 내용 |
|---|---|
| `SearchRewardTableDefinition` | 단계 범위와 D20 구간별 보상 행 |
| 보상 행 | 적용 단계 범위, D20 최소·최대 눈, 보상 항목 0개 이상 |
| 보상 항목 | 지급 대상(지역 주 자원 또는 특정 RESOURCE_TYPE), 비음수 수량 |

- 기본표는 GameConfig에 두고 RegionConfig에 별도 표가 없으면 사용한다. 지역별 표를 지정하면 그 표 전체를 사용한다. 일부 구간이 빠졌을 때 기본표와 임의로 섞지 않는다.
- 기본표와 지역별 표는 같은 정의 형식을 쓴다. 처음에는 직렬화 가능한 데이터로 구성하며, 보상표마다 별도 Manager나 독립 로딩 시스템을 만들지 않는다.
- 기본판의 보상 행은 `지역 주 자원 × 기존 표의 수량`만 가진다. 미발견 행은 비어 있는 항목 목록으로 표현한다.
- 확장 시 같은 행에 `지역 주 자원 × 2`, `의약품 × 1` 등을 넣을 수 있다. 이 수치는 구조 설명용이며 기본판의 지급량 변경이 아니다.
- ExplorationRules는 지역·단계·D20 눈과 적용할 정의를 받아 보상 행 하나를 선택한다. 상대 대상인 지역 주 자원을 실제 자원으로 해석하고, 같은 자원 항목을 합산하여 ResourceAmount 하나를 반환한다.
- 주 자원이 식량인 지역에서 `주 자원 +1`과 `식량 +1`이 함께 있으면 최종 식량 2개다. 항목 수와 자원 종류 수를 혼동하거나 합산한 뒤 원본 항목을 다시 지급하지 않는다.
- 보상 항목마다 추가 난수를 뽑지 않는다. 한 번의 D20으로 전체 묶음을 확정한다. UI도 종류별 재굴림을 요구하지 않는다.

RegionConfig의 주 자원은 기본표 해석과 지역 설명에 사용한다. 그것만으로 모든 수색 결과의 자원 종류를 제한하지 않는다. 기존 세 자원의 혼합은 데이터 확장이고, 새로운 자원·장비·인벤토리 규칙은 별도 설계 변경이다.

## 4. 사건 데이터와 판정

### 4.1 세 사건 처리 방식

| 방식 | 데이터 | 처리 |
|---|---|---|
| 즉시 결과형 | 상황과 확정 효과 | 진입 시 효과를 한 번 적용하고 결과 확인 상태 |
| 판정형 | 상황과 판정 행동 1개 | 대응 입력에서 D20을 한 번 굴리고 결과 확정 |
| 선택형 | 상황과 행동 2~3개 | 선택한 행동만 실행. 판정이 없으면 확정 효과 적용 |

행동에는 로컬 행동 ID, 버튼 문구, 판정 필요 여부, 적용 능력치, DC, 성공 효과, 실패 효과를 둔다. 판정 없는 행동은 성공/실패라는 임의 판정을 만들지 않고 확정 효과를 사용한다. 지나치기는 효과가 없는 행동이다.

효과는 현재 필요한 자원 증감, HP 증감, 소음 증감으로 제한한다. 한 결과에 여러 자원 효과 항목을 둘 수 있으며, 대상은 특정 자원 또는 `지역 주 자원`으로 지정한다. 후자는 적용 전에 현재 Region 정의의 자원으로 해석한다. 따라서 같은 보관함 사건을 세 지역에서 재사용하거나 복수 자원 보상을 구성할 수 있다. 초기 사건의 효과 값은 기존 기획서대로 유지한다.

자원 보상은 항상 현재 탐색의 임시 전리품에 적용한다. HP·소음과 전리품의 다음 값을 계산한 뒤 하나의 행동 결과로 반영한다. HP가 0이면 해당 탐색의 전리품을 폐기하고 사망 흐름으로 전환한다. 사건 결과 확인을 누를 때 효과를 다시 적용하지 않는다.

### 4.2 사건 추첨과 중복 처리

1. 현재 단계의 범주 확률표에서 사건 없음·기회·위험을 추첨한다.
2. 지역 목록에서 범주와 등장 단계가 맞는 사건 후보를 구한다.
3. 직전 단계와 다른 후보가 있으면 직전 단계 사건 ID를 제외한다. 후보가 그것뿐이면 중복을 허용한다.
4. 남은 후보에서 같은 확률로 하나를 뽑는다.

직전 단계에 사건이 없었다면 직전 단계 사건 ID도 비운다. 이것을 마지막으로 만난 사건 ID와 혼동하지 않는다. 전날의 기록은 다음 탐색에 이월하지 않는다.

잘못된 설정으로 후보가 없다면 기획서대로 사건 없이 진행하며 진단 로그를 남긴다. 정상 콘텐츠에서는 시작 전 검토로 후보 누락을 찾아 수정한다.

### 4.3 귀환 사건의 처리

기본 귀환 사건 `RETURN_001`은 일반 사건 추첨 목록에 넣지 않는다. GameConfig에 귀환 사건 ID·상황·행동 문구·능력치·DC를 두고, 실패 피해는 소음별 귀환 표에서 읽는다. 같은 피해를 사건 데이터에도 중복 저장하지 않는다.

귀환을 시작할 때 현재 소음과 위험 행을 고정한다. 위험 발생 판정은 한 번만 실행한다. 발생하면 행동 입력에서 D20을 굴리고, 성공은 피해 없음, 실패는 고정한 귀환 표의 피해를 적용한다. 이후 생존 여부를 확인하고 정산한다. 귀환 사건을 처리한 뒤 다시 위험 발생 판정을 호출하지 않는다.

귀환 사건의 화면과 주사위 표현은 일반 판정형 사건의 UI를 재사용한다. 향후 여러 귀환 사건을 추가할 때는 귀환 정의 목록과 추첨 규칙을 확장하되, 일반 사건의 임의 효과를 그대로 허용하지 않는다.

## 5. 게임 진행 상태와 명령

### 5.1 진행 상태

상태마다 클래스를 만드는 범용 State 패턴 대신 `GAME_PHASE`와 명시적인 전이 메서드로 시작한다.

| 상태 | 허용 행동 | 다음 처리 |
|---|---|---|
| `SHELTER` | 치료, 생존자·지역을 지정한 출발 | 첫 단계 사건 진입 |
| `EVENT_ACTION` | 현재 사건의 유효한 행동 선택 | 결과 확정 후 `RESULT` |
| `SEARCH_CHOICE` | 수색 또는 수색 생략 | 수색은 `RESULT`, 생략은 단계 종료 처리 |
| `STAGE_CHOICE` | 다음 단계 또는 귀환 | 새 사건 진입 또는 귀환 처리 |
| `RETURN_ACTION` | 귀환 대응 | 결과 확정 후 `RESULT` |
| `RESULT` | 현재 결과 확인 | 저장된 후속 흐름으로 이동 |
| `DAY_SUMMARY` | 정산 확인 | 다음 날 은신처 또는 종료 화면 |
| `GAME_OVER` | 새 게임 | 새 Session 생성 |

사건 진입·정산 계산은 동기적으로 끝내는 내부 처리이며 별도 입력 가능 상태로 만들지 않는다. 화면 애니메이션을 진행 상태 enum에 넣지 않는다.

RESULT의 후속 흐름은 세 가지면 충분하다: 사건 생존 후 수색, 수색 후 단계 종료, 사망 또는 귀환 판정 후 탐색 정산. 임의 콜백을 상태에 저장하는 대신 명시된 후속 종류를 기록한다.

- 즉시 결과형 사건은 입력을 기다리지 않고 효과를 적용한 뒤 RESULT로 간다.
- 일반 사건에서 사망하면 결과를 보여준 뒤 정산으로 간다. 수색은 열리지 않는다.
- 1~4단계 종료는 STAGE_CHOICE, 마지막 단계 종료는 자동 귀환 절차다.
- 수색 생략은 재수색할 수 없도록 바로 단계 종료 처리한다.
- 안전 귀환 또는 귀환 사건 미발생은 바로 정산으로 간다.
- DAY_SUMMARY에 들어갈 때 정산은 이미 완료되어 있다. 확인 버튼은 화면과 다음 입력 상태만 전환하며 자원을 다시 더하거나 날짜를 다시 올리지 않는다.

### 5.2 Session의 외부 명령 제안

| 메서드 | 핵심 검증 |
|---|---|
| `TryHeal` | 은신처 상태, 유효한 생존자, HP 부족, 의약품 보유 |
| `TryStartExpedition` | 은신처 상태, 살아 있는 생존자, 유효한 지역 |
| `TryChooseEventAction` | 사건 행동 상태, 현재 사건과 행동 ID 일치 |
| `TrySearch` / `TrySkipSearch` | 수색 선택 상태 |
| `TryAdvanceStage` | 다음 단계 선택 상태, 마지막 단계 아님 |
| `TryReturn` | 다음 단계 선택 상태 |
| `TryResolveReturn` | 귀환 대응 상태 |
| `TryConfirmResult` | 결과 ID와 현재 결과 상태 일치 |
| `TryConfirmDaySummary` | 현재 정산 상태 |

명령은 실제 구현에서 필요한 ID와 화면에 표시된 Revision을 받는다. 허용되지 않은 입력은 거절 이유를 반환하며 상태·난수·자원을 소비하지 않는다. 화면에서 버튼을 숨겼다는 이유로 검증을 생략하지 않는다.

수락한 명령에서 상태가 바뀌면 Revision을 증가시킨다. Presenter는 버튼 입력 시 해당 화면에 표시한 Revision을 전달한다. 동일 프레임의 중복 입력이나 이전 화면의 늦은 콜백이 다음 행동으로 재해석되지 않게 한다. Revision은 네트워크 동기화 기능이 아니라 로컬 입력 중복 방지용이다.

새 게임은 기존 상태의 일부만 초기화하지 않고 새 GameSession을 만든다. 날짜·HP·전리품·소음·직전 사건·미확인 결과를 함께 초기화한다.

### 5.3 하루 정산

`SurvivalRules`는 읽기 전용 현재 값과 규칙을 받아 정산 후 값과 정산 내역을 계산한다. Session이 결과를 한 번 반영한다.

순서는 기획서와 동일하게 전리품 반영 또는 폐기 → 전원 사망 → 목표 달성 → 기한 초과 → 식량 소비·부족 피해 → 전원 사망 재확인 → 다음 날이다. 종료가 결정되면 이후 계산을 중단한다.

정산 결과에는 완료한 날짜, 반영/상실 전리품, 식량 소비, 부족 피해, 사망자, 종료 사유, 다음 날짜를 보관한다. 현재 날짜가 이미 증가했어도 정산 패널은 완료한 날짜를 보여준다. 승리·패배가 결정된 경우 다음 날짜는 없다.

## 6. 난수와 결과 확정

### 6.1 난수 경계

`IRandomSource` 하나만 두고 `NextInt(minInclusive, maxExclusive)`를 정의한다. 실제 구현은 `System.Random`을 감싼 `GameRandom`, 검증에서는 미리 정한 정수 목록을 반환하는 대체 구현을 사용한다.

- D20: `NextInt(1, 21)`.
- 범주·발생 확률: `NextInt(0, 100)`을 누적 확률 경계와 비교한다.
- 사건 후보 선택: `NextInt(0, candidateCount)`.
- 확률 0%와 100%는 추가 난수 없이 각각 미발생·발생으로 처리한다.
- 후보가 없으면 난수를 뽑지 않는다. 후보가 하나면 해당 사건을 바로 사용한다.

Session만 게임 판정용 난수를 소비한다. 규칙에는 뽑힌 눈 또는 표본을 전달하고, UI의 깜빡이는 숫자나 효과음 선택은 게임 난수와 분리한다. 결과 표시를 다시 열었다고 난수가 다시 소비되지 않는다.

### 6.2 결과 데이터

명령 응답에는 수락 여부·거절 이유·현재 Snapshot을 둔다. 결과 확인이 필요한 명령은 Session에 읽기 전용 `ActionReport`를 보관한다.

ActionReport에는 결과 ID, 사건·행동 ID, 결과 종류, D20 눈·보정·합계·DC(해당할 때만), 성공 여부, 실제 자원·HP·소음 변화, 적용 전후 표시 값, 후속 흐름을 담는다. 수색은 성공 DC가 없는 보상 판정이므로 억지로 행동 판정 형식에 맞추지 않는다.

수색 ActionReport에는 확정한 보상 ResourceAmount 전체를 보관한다. Session은 모든 종류를 한 번의 상태 변경으로 임시 전리품에 더하고, 귀환 시에는 전리품 묶음 전체를 은신처에 반영한다. 사망 시에는 묶음 전체를 폐기한다. 확인·연출 재개는 묶음을 다시 지급하지 않는다.

UI는 주 자원 이름으로 표시 대상을 추정하지 않고 report의 양수인 자원을 모두 아이콘·수량으로 표시한다. 전체 0일 때만 미발견이다. 한 종류와 여러 종류를 같은 결과 표시 경로로 처리한다.

**결과는 연출 전에 확정하고 적용한다.** 주사위 애니메이션의 종료 콜백에서 보상을 더하지 않는다. 연출을 취소하거나 다시 표시해도 같은 결과를 사용한다. 이 원칙은 향후 연출 건너뛰기 기능을 추가할 때도 유지한다.

## 7. HM CodeBase 기반 UI MVP

### 7.1 화면별 구성

| 화면 | Model | View | Presenter |
|---|---|---|---|
| 은신처 | `ShelterModel_model` | `ShelterPanel_view : AView` | `ShelterPresenter_presenter : APresenter` |
| 탐색 | `ExplorationModel_model` | `ExplorationPanel_view : AView` | `ExplorationPresenter_presenter : APresenter` |

- Model은 Snapshot으로 만든 표시 데이터와 선택 중인 생존자·지역 ID 등을 가진다. 치료 결과나 전리품 원본을 수정하지 않는다.
- View는 Text·Image·Button 등의 참조, 표시 함수, 클릭 이벤트, 화면 연출을 담당한다.
- Presenter는 View 이벤트를 받아 Provider에 요청하고, Provider가 전달한 확정 데이터를 Model에 반영해 View를 갱신한다.
- 버튼·텍스트 하나마다 MVP를 만들지 않는다. 주사위, 정산, 종료는 공통 하위 View로 시작하고 독립적인 화면 책임이 커졌을 때만 Presenter를 분리한다.
- 게임 규칙과 GameSession은 UI Model도 Presenter도 아니다. MVP는 UI에만 적용한다.

### 7.2 실제 HM API에 맞춘 수명

HM CodeBase 1.0.1의 AView는 `Open()`, `Close()`, `Clear()`를 제공하며, APresenter는 `Open()`, `Close()`, `Dispose()` 구현을 요구한다. 이 두 클래스는 이전에 확인한 1.0.0 소스와 동일하므로 기존 MVP 구성을 유지한다. 제네릭 Model 자동 연결, 비동기 수명 API, 자동 구독 해제는 제공하지 않는다.

- `Open()`: 중복 열림을 막고 화면 열림 세대를 갱신한 뒤 버튼 이벤트 구독, 화면 수명 생성, 현재 Snapshot 표시를 수행한다.
- `Close()`: 먼저 닫힘 상태를 기록하고 현재 열림 세대를 무효화한 뒤, 화면 작업 취소, 버튼·알림 구독 해제, View 닫기를 수행한다. 반복 호출해도 안전하게 한다.
- `Dispose()`: Close 후 참조와 소유 자원을 해제한다. Provider 종료 시 호출한다.
- 열림·닫힘 애니메이션이 필요하면 `PlayOpen_async`, `PlayClose_async` 같은 별도 메서드를 정의한다. HM의 동기 메서드 시그니처를 임의로 바꾸지 않는다.

View.Close는 확인한 구현상 GameObject를 비활성화할 뿐이다. 화면 작업 취소나 이벤트 구독 해제가 자동으로 보장되지 않으므로 Presenter가 수행해야 한다. 재개 시에는 Session의 미확인 결과를 다시 표시하며 판정을 다시 실행하지 않는다.

### 7.3 EventProvider의 사용 범위

핵심 요청과 연출 순서는 Presenter → Provider의 명시적인 호출과 반환값으로 연결한다. HM EventProvider는 필요할 경우 확정 후 부가 알림에 사용한다. 첫 구현부터 모든 입력과 결과를 전역 이벤트로 바꾸지 않는다.

1.0.1의 `Publish<T>`는 구독자 목록을 `ToArray()`로 복사한 뒤 동기적으로 호출한다. 따라서 콜백 안에서 Subscribe/Unsubscribe를 수행해도 현재 순회 목록 자체는 바뀌지 않는다. 기존 설계서의 **발행 중 구독 변경 금지**와 **해제를 Publish 반환 후로 미루는 제약**은 제거한다.

다만 복사된 목록과 현재 화면 수명은 별개이므로 다음 규칙을 적용한다.

- 발행 중 해제한 콜백도 현재 발행의 복사본에 남아 있으면 호출된다. 이후 발행부터 해제가 반영되며, 콜백 안에서 다시 Publish한 경우에는 그 중첩 발행 시작 시점의 목록을 사용한다.
- Presenter가 구독할 때 현재 화면 열림 세대를 캡처한 콜백을 만들고, 그 델리게이트를 저장해 정확히 해제한다. 콜백 실행 시 열린 상태·Dispose 여부·캡처한 세대를 확인한다. 같은 발행 중 화면을 닫았다 다시 열어도 이전 구독 콜백이 새 화면을 갱신하지 않게 한다.
- 중복 Subscribe 방지는 여전히 없다. 한 번 Open에서 한 번만 구독하고 Close에서 해제한다. 새로 만든 람다로 Unsubscribe하지 않는다.
- 구독자별 예외 격리도 없다. 한 콜백에서 예외가 전파되면 해당 Publish의 이후 콜백이 실행되지 않을 수 있다. 부가 알림 콜백은 필요한 예외 처리와 기록을 자체 경계에서 수행하고, 게임 정산을 알림 처리 성공에 의존시키지 않는다.
- 구독 목록을 복사하는 발행마다 배열 할당이 발생한다. 사건 결과·화면 변경 같은 낮은 빈도의 알림에 사용하고, 매 프레임 주사위 숫자나 애니메이션 갱신은 View 내부에서 처리한다.

게임 상태는 알림 발행 전에 확정한다. 화면 전환은 Provider의 명시적인 호출 흐름으로 유지하며, 이벤트 구독 순서로 다음 게임 단계를 결정하지 않는다.

SessionProvider는 현재 한 판을 소유하는 데 필수적이지 않으므로 도입하지 않는다. HM CodeBase를 사용한다는 이유만으로 모든 기능을 동시에 채택하지 않는다.

### 7.4 JSON 유틸리티와 향후 저장 기능

저장·불러오기는 게임 기획서의 확장 후보 상태를 유지한다. 기본판의 ScriptableObject 콘텐츠를 JSON으로 교체하지 않는다. 저장 기능을 추가할 때 사용할 API 기준만 이번 업데이트에 맞춰 정리한다.

| API | 1.0.1 동작 | 설계 반영 |
|---|---|---|
| `TryParseJson<T>(json, out result)` | Newtonsoft.Json 변환 성공 여부를 bool로 반환 | 변환 성공과 저장 데이터의 필수 값·버전·ID 유효성을 따로 검사 |
| `ParseJson<T>(json)` | 기존 호출 유지, 실패하면 기본값 반환 | 실패와 정상 기본값을 구분해야 하는 복원 경로에는 TryParseJson 사용 |
| `TryWriteJson(filePath, obj)` | Newtonsoft.Json으로 직렬화·파일 쓰기, 성공 여부를 bool로 반환 | 반환값이 true일 때만 저장 완료 처리 |

- 참조 타입의 JSON `null`도 TryParseJson에서는 성공일 수 있다. true만 확인하고 복원을 진행하지 않고 result의 null 여부와 내용도 검사한다.
- 저장 대상은 버전·콘텐츠 ID·진행 값이 들어 있는 일반 C# 저장 데이터로 정의한다. View, GameObject, ScriptableObject, UniTask·취소 토큰, 델리게이트를 직렬화하지 않는다.
- 이전 JsonUtility 저장 형식과의 호환을 자동으로 가정하지 않는다. 특히 `[SerializeField]` private 필드와 Unity 전용 타입은 별도 변환·검증 대상이다.
- TryWriteJson은 기존 void에서 bool 반환으로 바뀌었다. 일반 메서드 호출과 달리 `Action<string, object>`에 직접 연결하는 방식은 맞지 않는다. 저장 결과를 확인하는 별도 호출 경계를 둔다.
- 유틸리티는 동기 파일 쓰기이며 원자적 교체·백업·취소를 제공하지 않는다. 저장을 도입할 때 경로와 실패 처리, 교체 방식을 함께 설계한다. 메서드 이름이나 UniTask 호출 래퍼만으로 비동기·취소 가능 저장이 되는 것은 아니다.
- HM Util 호출은 Unity 연결부에 둔다. Core가 HM CodeBase나 UnityEngine에 의존하지 않는 원칙은 유지한다.

## 8. Provider와 UniTask 흐름

### 8.1 Provider의 범위

`LastSupplyGameProvider`는 Scene에 한 개 배치하는 Unity 컴포넌트로 설계한다. 콘텐츠 카탈로그와 두 화면 View를 참조하고, GameSession·Presenter와 비동기 수명을 소유한다. Presenter에는 Provider 참조를 명시적으로 전달한다.

기본 타입은 `MonoBehaviour`이며, 처음에는 전역 정적 접근이나 DontDestroyOnLoad를 요구하지 않는다. 다른 Scene까지 유지하는 필요가 생기면 별도로 결정한다.

HM CodeBase 1.0.1의 `ASingletone<T>`는 Awake에서 인스턴스를 등록하고 Instance에서 캐시를 재사용한다. 최초 탐색에는 비활성 GameObject도 포함하며, 존재하지 않을 때만 자동 생성한다. 중복 제거 대상은 GameObject 전체가 아니라 해당 컴포넌트다.

LastSupplyGameProvider는 Inspector의 콘텐츠·View 참조가 필요하므로 Scene에 명시적으로 배치하고 시작 시 단일 인스턴스와 필수 참조를 확인한다. 자동 생성된 빈 객체를 게임 초기화로 취급하지 않는다. EventProvider 등 HM 싱글톤을 사용할 경우 준비 단계에서 참조를 확보해 필요한 Presenter에 전달하고, 종료·해제 경로에서 Instance를 다시 조회해 객체를 생성하지 않는다.

향후 LastSupplyGameProvider를 `ASingletone<LastSupplyGameProvider>`로 전환한다면 `base.Awake()`를 호출해야 한다. 중복 컴포넌트의 Destroy는 예약 처리이므로 base.Awake 호출만으로 파생 Awake의 나머지 코드가 중단되지는 않는다. 등록된 인스턴스가 자신인지 확인한 뒤에만 Session·Presenter를 초기화한다. 또한 비활성 객체의 최초 검색 결과가 곧 초기화 완료를 뜻하지는 않으므로, Provider의 준비 완료 전에 UI 요청을 받지 않는다. 이 조건은 전환 시 적용할 기준이며 현재 기본 설계를 싱글톤으로 변경하는 것은 아니다.

### 8.2 수색 한 번의 처리

1. Presenter의 `OnSearchActioned()`가 표시된 Revision으로 Provider에 요청한다.
2. Provider가 활성 작업 여부를 확인하고 **첫 await 전에** 입력을 잠근다.
3. Session의 `TrySearch`가 상태·Revision을 검사한다. 거절 시 난수나 보상을 소비하지 않는다.
4. 수락 시 D20을 한 번 뽑고 ExplorationRules로 지역·단계의 보상 묶음(ResourceAmount)을 계산한다.
5. Session이 보상 묶음의 모든 종류를 전리품에 한 번 반영하고 ActionReport를 저장한 뒤 RESULT로 이동한다.
6. Provider가 `PlayResult_async(report, token)`을 await한다. 주사위 연출은 report의 눈으로 끝나야 한다.
7. 연출 중에는 적용 전 표시 값을 유지하고, 결과를 공개할 때 적용 후 값과 변화량을 함께 보여준다. 숫자 갱신으로 주사위 결과를 미리 노출하지 않는다.
8. 연출이 끝나면 현재 결과 확인 버튼만 허용한다. 확인 입력이 Session의 `TryConfirmResult`를 통과해야 다음 단계 선택이 열린다.

사건 행동과 귀환 행동도 같은 결과 표시 경로를 사용한다. 즉시 결과형은 주사위 연출만 생략한다. 주사위, 피해 표시, 결과 패널을 서로 독립적인 Forget 호출로 동시에 시작하지 않는다.

### 8.3 취소와 재시작

- **Provider 수명:** Unity 오브젝트 파괴와 연결된 취소 토큰.
- **게임 수명:** 새 게임마다 만드는 CancellationTokenSource. 재시작 시 이전 게임의 모든 연출과 대기를 취소한다.
- **화면 수명:** Presenter.Open에서 시작하고 Close/Dispose에서 취소한다. 게임 수명과 View 파괴 수명에 연결한다.
- 화면 비활성화만으로 파괴 토큰이 취소되지는 않는다. 화면 닫힘에는 명시적인 취소가 필요하다.

모든 대기·연출은 해당 토큰을 전달받는다. 새 게임에서는 기존 게임 토큰 취소 → Presenter 닫기·구독 해제 → 새 Session·수명 생성 → 은신처 표시 순서를 따른다. 이전 작업의 취소 후 정리가 끝나기 전에 새 UI를 공유한다면, 아래 소유권 검사로 이전 작업의 접근을 차단한다.

Provider는 게임 세대 번호와 활성 작업 ID를 관리한다. await 이후와 finally에서 화면 갱신·입력 잠금 해제를 하기 전에 여전히 같은 게임·같은 작업인지 확인한다. 이전 작업이 늦게 종료되면서 새 게임의 잠금을 풀지 않도록 한다.

취소는 이미 확정한 주사위 결과의 취소나 재굴림을 뜻하지 않는다. 화면만 닫혔다면 Session의 결과를 유지하고 다시 열 때 표시한다. 새 게임이라면 이전 Session 전체를 폐기한다. 예기치 않은 연출 오류는 기록하고 현재 확정 결과를 연출 없이 보여줄 수 있도록 복구한다. 오류를 성공 처리하거나 새로운 보상을 적용하지 않는다.

핵심 비동기 작업은 `UniTask` 반환과 await를 사용한다. Unity 클릭 콜백의 최외곽에서만 예외 처리를 갖춘 Forget 호출을 허용한다. 일반적인 정상 취소와 실제 오류를 구분하며, 예외 전체를 무시하지 않는다. 중첩된 비동기 함수마다 별도 게임 토큰을 만들지 않는다.

## 9. 초기 콘텐츠 검증

게임 시작 전에 다음을 검사하고, 문제가 있으면 해당 ID와 항목을 표시해 시작을 막는다. 후보 누락을 포함한 정상 콘텐츠 오류를 런타임의 조용한 보정에 의존하지 않는다.

- 콘텐츠 ID 중복, 지역의 존재하지 않는 사건 참조, 시작 생존자·지역 누락.
- 단계 확률표의 합계 100%, 음수 확률, 단계 범위 누락.
- 적용할 각 수색 보상표의 단계·D20 1~20 전체 커버, 중첩·누락, 음수 보상, 유효하지 않은 지급 대상. 지역별 표가 지정되었으면 해당 표 전체를 검사.
- 보상 항목이 비어 있는 미발견 행은 유효한 데이터다. 주 자원과 특정 자원이 겹치는 항목은 합산 규칙으로 처리.
- 소음 0~최대치의 귀환 표 커버, 확률 범위, 음수 피해.
- 최대 HP·제한 일수·단계 수·목표량의 유효성, 초기 자원의 음수 여부.
- 즉시 결과형의 확정 효과, 판정형 행동 1개, 선택형 행동 2~3개와 고유 행동 ID.
- 지역·단계별 기회·위험 후보 존재, 귀환 사건의 일반 추첨 제외.

런타임에 예상하지 못한 후보 없음이 발생하면 4.2의 방어 처리를 따른다. 진단 로그는 개발용이며 플레이어에게 클래스명이나 설정 경로를 그대로 노출하지 않는다.

## 10. 파일 배치와 구현 순서

### 10.1 폴더 제안

```text
Assets/LastSupply/
  Scripts/
    Core/             GameSession, 상태·결과, 규칙, 난수 경계
    Content/          ScriptableObject 정의, 변환·검증
    Game/             LastSupplyGameProvider
    UI/
      Shelter/        Model / View / Presenter
      Exploration/    Model / View / Presenter
      Common/         주사위·정산·종료 표시
  Data/               규칙·생존자·지역·사건 에셋
  Tests/
    EditMode/         규칙·Session·콘텐츠 검증
    PlayMode/         UI 연결·비동기 수명 검증
```

폴더는 첫 구현 시 필요한 것부터 만든다. Core는 UnityEngine·UniTask·HM CodeBase를 참조하지 않는다. 어셈블리를 분리할 때는 Core와 Unity 연결부, 테스트 정도로 시작하며 기능마다 asmdef를 만들지 않는다. 현재 문서 작성에서 폴더·asmdef·에셋을 생성하지 않는다.

### 10.2 구현 순서

1. **사용 라이브러리와 데이터 경계:** 현재의 UniTask·HM CodeBase 연결과 컴파일 상태를 확인하고 기본 정의·상태를 만든다. UPM 등록과 Assets 플러그인 배치를 구분하며 중복 설치하지 않는다.
2. **순수 C# 첫 탐색:** 지역 1곳·생존자 1명·세 사건·귀환을 GameSession으로 처리한다. 고정 난수로 흐름을 확인한다.
3. **HM UI 연결:** 은신처·탐색 MVP와 Provider를 연결하고 숫자와 버튼만으로 한 번의 탐색을 완료한다.
4. **UniTask 연출과 취소:** 공통 주사위·결과 표시를 연결하고 재시작·화면 닫힘·연타를 확인한다.
5. **기본 완성본:** 다일 정산·치료·승패·재시작, 생존자 2명·지역 3곳·일반 사건 5개로 확장한다.
6. **콘텐츠 추가 검증:** 기존 사건 효과만 사용하는 새 사건과 지역 데이터를 넣어 진행 코드 수정 없이 동작하는 범위를 확인한다. 개발용 복수 자원 보상표로 결과·전리품·정산·UI의 공통 처리를 확인한다. 기본판의 실제 수급은 기존 단일 주 자원 보상표를 기준으로 검증한다.

첫 탐색 시제품은 일반 규칙을 그대로 사용하되 하루 정산·엔딩 연결 이전까지만 확인한다. 시제품 전용 게임 규칙을 별도로 만들어 완성본에서 다시 작성하지 않는다.

## 11. 필요한 검증과 포트폴리오 설명

### 11.1 순수 C# 검증 계획

- D20 경계값 6/7/15/16/19/20과 깊이에 따른 수색 보상.
- 기본표·지역별 표 선택, 미발견·단일·복수 보상의 ResourceAmount 결과. 지역 주 자원과 같은 특정 자원 항목의 합산.
- 복수 보상에서도 수색 D20을 한 번만 소비하고, 묶음 전체를 한 번만 전리품에 반영. 귀환 시 모두 반영하고 사망 시 모두 폐기.
- 행동 합계가 DC와 같을 때 성공, 1 작을 때 실패. 눈 1·20의 별도 자동 판정 없음.
- 사건 범주 경계, 후보 없음·한 개·여러 개, 직전 단계 중복 제외.
- 귀환 확률 0%·100%, 위험 판정 1회, 실패 후 생존과 사망.
- 마지막 단계 종료, 사건 중 사망, 임시 전리품 반영·폐기의 정확히 한 번 처리.
- 마지막 날 목표 달성, 기한 초과, 식량 부족 후 전원 사망 순서.
- 잘못된 상태·ID·Revision 요청이 상태와 난수를 바꾸지 않음.
- 같은 결과를 두 번 확인하거나 같은 수색 요청을 반복해도 중복 보상 없음.

GameSession은 MonoBehaviour 없이 구동할 수 있어야 한다. 테스트에서는 임의의 성공을 기대하지 않고 지정된 난수로 정확한 상황을 만든다.

### 11.2 Unity 연결 검증 계획

- 연출 중 클릭·확인 연타가 중복 행동을 만들지 않음.
- 결과 적용 후 연출 취소·화면 재열기에서 같은 결과가 표시됨.
- 재시작 후 이전 UniTask가 새 UI·입력 잠금·보상을 건드리지 않음.
- 반복 Open/Close/Dispose에서 버튼과 EventProvider 구독 중복 없음.
- EventProvider 발행 중 해제·재구독에서 현재 발행의 복사본과 다음 발행의 목록이 구분됨. 해제된 콜백이 뒤늦게 호출되어도 닫힌 화면이나 새 열림 세대를 갱신하지 않음.
- 부가 알림 콜백 오류가 이미 확정된 게임 상태를 되돌리거나 다음 입력을 영구적으로 잠그지 않음.
- Provider의 필수 참조·중복 배치를 시작 시 확인하고, 종료 중 HM Instance 재조회로 새 객체를 만들지 않음. 싱글톤 베이스를 채택한다면 비활성 객체 검색과 중복 Awake의 초기화 차단도 확인.
- 주사위 표시, 실제 전리품, 귀환 위험 안내가 같은 확정 데이터를 사용함.
- 단일·복수 보상의 모든 자원 아이콘·수량이 같은 결과 화면에 표시되고, 전부 0인 결과만 미발견으로 표시됨. 재열기와 확인 연타에서 묶음 재지급 없음.
- 새 게임부터 승리·두 패배 사유·재시작까지 실제 진행 가능.

이는 앞으로 수행할 검증 계획이다. 설계서 작성만으로 컴파일·테스트·Play Mode가 검증된 것은 아니다.

저장 기능을 도입하는 시점에는 정상 JSON, 손상된 JSON, JSON null, 유효하지 않은 콘텐츠 ID, 쓰기 실패를 별도로 검증한다. 현재 기본판의 구현 완료 기준에 저장 기능을 추가하는 것은 아니다.

### 11.3 포트폴리오에서 설명할 지점

1. 게임 규칙과 Unity 표현을 분리해 화면 없이 진행을 검증한 이유.
2. 주사위 결과 확정과 연출을 분리하여 취소·연타에도 보상을 한 번만 적용한 방식.
3. HM CodeBase의 UI MVP를 화면에만 적용하고 게임 상태 원본을 별도로 둔 이유.
4. 같은 흐름에 사건·지역·생존자 데이터를 추가하는 실제 확장 사례.
5. UniTask의 게임·화면 수명을 관리하여 재시작 뒤 이전 작업을 차단한 사례.

실제로 구현하고 확인한 항목만 포트폴리오 성과로 설명한다.

## 12. 명명 규칙과 후속 결정

- 사용자 지정 C# 규칙을 따른다. private/protected 필드는 `_exampleVariable`, 정적 필드는 `s_exampleVariable`, 상수·readonly 필드는 `EXAMPLE_VARIABLE`을 사용한다.
- 일반 메서드는 PascalCase, 비동기 완료를 기다리거나 진행 중인 작업을 반환하면 `_async`, 이벤트 바인딩은 `OnExampleActioned` 형태를 사용한다.
- 열거형 이름과 요소는 UPPER_SNAKE_CASE, 인터페이스는 I 접두사, 추상 클래스는 A 접두사를 사용한다.
- UI MVP 클래스는 `_model`, `_view`, `_presenter`를 사용하고 Unity 참조에는 `_searchBtn`, `_statusTxt`, `_locationImg`처럼 접미사를 붙인다.
- HM CodeBase·UniTask의 기존 API 이름은 패키지 그대로 사용한다. 프로젝트 규칙에 맞추기 위해 외부 패키지를 수정하지 않는다.

이 설계의 핵심 경계는 **Session이 상태를 확정하고, Provider가 흐름과 작업 수명을 연결하며, Presenter가 확정 결과를 화면에 보여주는 것**이다. 구체적인 클래스 수는 첫 탐색 구현에서 필요한 만큼만 늘린다. 게임 기획의 수치는 코드 상수가 아니라 설정 데이터에서 관리하며, 밸런스 조정은 본 설계서에서 임의로 바꾸지 않는다.
